Zero-config caching: how the hit rate is earned

ridge-4 ridge-3 (stable) ridge-2 EOL

Caching on Ridgeline is on by default and needs no manifest. This guide explains what we key on, why misses happen anyway, and how to read the hit meter when it drops. If you want rules instead of reasoning, jump to the commands.

The key, in one sentence

The cache key is the pair toolchain-hash + input-tree-hash. We hash the input tree with a rolling Merkle build — no lockfile diffs, no git shims, no timestamps. Two branches with identical content share artifacts.

# what ridgeline prints on a hit
cache hit "toolchain:rust-1.84+aarch64" "tree:9f2c…d41e"
  restored 1,208 artifacts in 3.4s  (hit rate window 92.4%)

Why misses still happen

Three causes account for nearly every miss we see, in order of frequency: a build reads the clock, an env variable leaks into a compile, or a tool writes absolute paths into outputs. Each is detectable from the timeline before it is detectable from the meter.

A hit rate you cannot explain is a hit rate you cannot keep. Read the misses before tuning the knobs.

Commands

Most cache questions are answered by two commands. ridge cache explain <job> prints the key and the diff that caused a miss; ridge cache gc --older-than 30d trims the local mirror. Run them from the console terminal or any runner you have reserved.

Runners read the island; the ledger is the truth

Every restore is recorded into an append-only ledger. Meter lines on the console page are computed from that ledger, which is why the hit rate never disagrees with the bill.
